Adaptive Selection Cache · Go

Experiment with cache eviction policies.

as-cache runs several eviction policies at once. One is active and serves every request; the rest run as shadows that see each key, never its value, and answer "would I have had this?" Once per epoch a multi-armed bandit selects the policy for the next epoch; optional stability gates can restrict switching.

This is experimental research software. For a general-purpose production cache, start with otter or theine; see the measured comparison. Automatic switching has not established a general advantage.

7 policies + 2 experimental FIFO arms planned for v0.5 Thompson sampling Go 1.25+ MPL 2.0 pre-1.0, v0.4 candidate

How it works

Per request

The active policy stores real values and serves the caller. A shared sampler gates the shadow fan-out, so shadows track a miniature of the same substream and fewer requests fan out to every shadow.

Per epoch

Every arm reports counts over the same sampled keyspace. Counts are not scaled up; miniature shadows can still change rates and rankings. The bandit uses these measurements to select a policy.

On switch

Optional stability gates limit switching; a migration strategy (cold, warm, or gradual) moves data so a switch never serves a shadow's placeholder as a real value.

Quick start

go get github.com/sshaplygin/as-cache
go get github.com/sshaplygin/as-cache/policies
go get github.com/sshaplygin/as-cache/bandit
lru, _ := policies.NewLRU[string, int](10000)
twoQ, _ := policies.NewTwoQueue[string, int](10000)

cache, err := ascache.NewAdaptiveCache(
    []ascache.Policy[string, int]{lru, twoQ},
    bandit.NewThompson(0.9, 1), // discount, seed
    &ascache.Settings{EpochDuration: time.Minute, ShadowSampleRate: 0.05},
)
if err != nil {
    return err
}
defer cache.Close()

cache.Add("k", 1)
v, ok := cache.Get("k")

Prefer measurement without the switching? ObserveOnly mode keeps the configured policy active while Advice() reports measured rankings. Sampling can change those estimates and measurement still adds overhead — see advisor mode.

What the evidence says

The current dataset contains twelve trace workloads and three consecutive measurement batches. Randomness and asynchronous maintenance produce variation; observed ranges do not bound future runs. Read the generated tables and provenance.

What to investigate

Experiments it supports

  • Compare policy rankings on a workload whose reuse pattern is unknown.
  • Measure how changing traffic, epoch length and migration affect selection.
  • Collect advice with switching disabled; account for measurement overhead and sampling distortion.

Skip it when

  • You have already measured your traffic and know which policy wins. Use that policy directly.
  • The hot path is latency-critical at single-digit nanoseconds.
  • You need a hard memory ceiling, or cannot give it enough traffic per epoch to measure anything.
  • Your keyspace fits in the cache — every policy scores the same when nothing is evicted.
